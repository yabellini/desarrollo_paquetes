¿Qué es un paquete?

Para calmar tus temores, recordá que no es más que una carpeta organizada de una manera específica.

— Sébastien Rochette

Una carpeta bien organizada que puede contener:

  • 🧑‍💻 código
  • 📖 documentación
  • 📊 datos

Del script al paquete

  1. Consola: cerrás R y se perdió.
  2. Script: lo guardás, pero lo copiás y pegás en cada proyecto.
  3. Funciones: mejor, pero viven en un script.
  4. Paquete: funciones, datos y documentación juntos. Se instala una vez y se usa con library().

¿Por qué crear un paquete?

Para compartir código y datos con:

  • vos (y tu yo del futuro),
  • las personas con las que trabajás,
  • las personas que hacen un trabajo parecido al tuyo.

Y para aprender: buenas prácticas, herramientas, y poder contribuir a otros paquetes.

Regla práctica: si una función la usás en más de un proyecto, ya merece un paquete.

Las herramientas

usethis crea archivos y carpetas
devtools carga, documenta, testea, revisa, instala
roxygen2 documentación: páginas de ayuda
testthat tests
cli mensajes y errores claros
pak instalar paquetes y comprobar nombres

¿Cuál es correcta?

  1. Un paquete solo puede tener funciones.
  2. Para crear un paquete hay que publicarlo en CRAN.
  3. Un paquete es una carpeta organizada que puede tener código, documentación y datos.
  4. Para crear un paquete hay que saber programar en C.

2. Crear el paquete

Un buen nombre

  • Solo letras, números y puntos.
  • Empieza con letra, no termina con punto.
  • Sin guiones ni guiones bajos.
pak::pkg_name_check("dichosos")

⚠️ Solo conoce malas palabras en inglés.

💻 En vivo: crear el paquete

pak::pkg_name_check("dichosos")
usethis::create_package("/Users/yabellini/Documents/GitHub/dichosos")
devtools::check()
usethis::use_mit_license("Tu Nombre")
devtools::check()

Lo que creó usethis

dichosos/
├── DESCRIPTION     ← metadatos
├── NAMESPACE       ← no se toca a mano
├── R/              ← las funciones
├── .Rbuildignore   ← lo que no es parte del paquete y se debe ignorar al construirlo
└── dichosos.Rproj  ← proyecto de RStudio (en Positron no está)

devtools::check()

  • ERROR: algo grave. Arreglar.
  • WARNING: probablemente mal. Arreglar.
  • NOTE: para mirar.

El objetivo: 0 errors ✔ | 0 warnings ✔

Qué hizo document()

  1. Escribió man/dicho_al_azar.Rd → la página de ayuda.
  2. Escribió export(dicho_al_azar) en NAMESPACE.

Nunca edites a mano NAMESPACE ni los archivos de man/.

Atajo: Ctrl/Cmd + Shift + D

Exportadas e internas

  • Con @export: pública. Se usa después de library(dichosos).
  • Sin @export: interna. Solo para otras funciones del paquete.

load_all() es generosa: te deja usar todas. Por eso a veces nos olvidamos del @export.

7. Tests

De la consola a los tests

Un test es un experimento de la consola, guardado, que se corre solo y avisa si algo cambió.

usethis::use_testthat(3)
usethis::use_test("dicho_al_azar")

💻 En vivo: un test

test_that("dicho_al_azar() devuelve un solo texto", {
  resultado <- dicho_al_azar()
  expect_type(resultado, "character")
  expect_length(resultado, 1)
})

test_that("dicho_al_azar() avisa si no conoce el país", {
  expect_error(dicho_al_azar(pais = "Narnia"), "Narnia")
})
devtools::test()

¿Cómo testeo algo al azar?

No sé qué dicho va a salir.

Pero sé cómo tiene que ser:

  • un texto,
  • de largo 1,
  • que esté en los datos del país pedido.

9. La IA en el ciclo de desarrollo

Dónde ayudan las herramientas de IA y dónde no

¿Por qué al final?

Hoy hicimos todo a mano, a propósito.

Ahora sabés qué hace cada paso.

Eso te permite revisar lo que hace una herramienta de IA.

La tarea no es el trabajo

Si me siento a hacer música porque quiero hacer músicaentregarme la canción ya hecha es entender todo al revés.El proceso no era un obstáculo que había que sortear para llegar al resultado.

The task isn’t the job, Sunil Pai.

En un taller, el proceso es el objetivo.

El ciclo clásico no cambia

  1. Escribir la función en R/
  2. load_all() y probar en la consola
  3. use_test() y escribir tests
  4. test() hasta que pasen
  5. document()
  6. check()
  7. Reiniciar R

Cambia quién escribe cada parte.

Qué cambia con la IA

La IA Vos
Código lo escribe lo probás y lo entendés
Tests le encantan que sean pocos y fallen cuando deben
Docs un borrador tu voz, para personas
check() arregla lo que encuentra lo corrés siempre
Datos limpia y transforma son tu responsabilidad

Lo que pedimos en rOpenSci

  • Revisá todo lo generado con IA antes de que lo lea otra persona.
  • La comunicación personal la escribís vos, nunca la IA.
  • Usarla para traducir está bien.

Siempre, siempre, aclará tu uso de la IA.

Software Review in the Era of AI, blog de rOpenSci.

Tres formas de usar un modelo

Cómo Ejemplos
Chat Conversás en una página web; vos copiás el resultado Copilot en github.com, claude.ai, ChatGPT
Cliente Conecta el modelo con tu editor o tu código de R Copilot en Positron o RStudio, ellmer
Agente Hace cosas en tu computadora: edita archivos, corre código Posit Assistant, Claude Code, Codex

Más autonomía → más importante revisar.

¿Qué es un agente?

Un modelo, adentro de un programa que le da herramientas, corriendo en un ciclo, usando esas herramientas para lograr un objetivo.

Hadley Wickham y Jenny Bryan.

  • Herramientas: leer, escribir, editar, correr R, correr comandos, buscar en la web.

Gratis con tu cuenta de GitHub

GitHub Copilot Free: con cualquier cuenta personal de GitHub.

  • Chat en el navegador: https://github.com/copilot
  • Cliente en Positron, RStudio y VS Code
  • Tiene un límite mensual de uso

Estudiantes, docentes y personas que mantienen proyectos de código abierto pueden pedir planes más completos gratis.

Riesgos: lo que no se puede deshacer

  • Editar archivos sin Git
  • Borrar sin copia de seguridad
  • Mandar un correo, publicar algo
  • Revelar un secreto

Usá Git siempre. Es tu botón de deshacer.

Pedidos cortos y precisos

  • Usá las palabras del tema: load_all(), @export, snapshot.
  • Achicá el alcance: este paquete, esta función.
  • Pedí pruebas: “¿dónde dice eso?”
  • Conversaciones cortas: empezá de nuevo seguido.

Cuánto delegar: más riesgo, más controles tuyos

💻 En vivo con Copilot: pedirlo bien

En https://github.com/copilot, con el repositorio de dichosos:

Agregá a dichosos la función dichos_por_tema(tema) en R/dichos_por_tema.R. Usá R base, sin dependencias nuevas. Si el tema no existe, dá un error con cli::cli_abort() que liste los temas, como en dicho_al_azar(). Documentala con roxygen2 y exportala. Tests cortos. Antes de escribir código, mostrame un plan.

Después: leer el plan → pedir el código → copiarlo al paquete → mirar los cambios en Git → load_all() → check().
